# Поддержка и изменения — Kanban Board

Это руководство для тех, кто поддерживает проект, вносит изменения или развивает функционал.

## Общий подход

Проект должен оставаться простым, стабильным и понятным. Каждое изменение должно:

- иметь ясную цель;
- не ломать текущую административную логику;
- быть документировано;
- проходить базовое тестирование.

## Процесс изменения

### 1. Откройте issue / задачу

Если вы вносите правку, начните с описания задачи:

- что именно меняем;
- почему это важно;
- какой пользовательский сценарий затрагивается.

### 2. Создайте ветку

Именуйте ветку так:

- `feat/<описание>` — для новой функциональности;
- `fix/<описание>` — для исправления багов;
- `docs/<описание>` — для документации.

### 3. Вносим изменения

#### Backend

- Новые маршруты добавляются в папку `routers/`.
- Маршруты, связанные с авторизацией, должны использовать `routers/auth.py`.
- В `routers/admin.py` поддерживаются только действия администратора.
- Для новых моделей расширяйте `models/models.py`.
- С сохранением данных используйте `SessionLocal` из `database.py`.

#### Frontend

- Верстка находится в `templates/`.
- Шаблоны Jinja2 используются для серверного рендеринга.
- JS-логика должна быть максимально простой и безопасной.
- Для форм и кнопок лучше использовать `data-*` атрибуты вместо сложных inline-`onclick`.

### 4. Тестирование

Запустите базовые тесты:

```bash
python -m unittest discover tests
```

Если добавили новую функциональность, проверьте ручные сценарии:

- вход в систему;
- создание пользователя;
- смена пароля;
- добавление/удаление подэтапа;
- работа с задачами на доске.

### 5. Обновление документации

После изменения функциональности обязательно обновите:

- `README.md` — если изменился способ запуска, функционал или структура;
- `docs/README.md` — если добавился новый раздел документации;
- `docs/MAINTENANCE.md` — если процесс поддержки изменился.

### 6. Коммит и PR

Коммит должен быть коротким и информативным.

Примеры:

- `feat: добавлен сброс пароля в админке`
- `fix: убран invalid onclick из шаблона admin.html`
- `docs: добавлено руководство по поддержке`

В PR укажите:

- что изменено;
- почему;
- как проверить.

## Поддержка проекта

### Что проверять первым

1. Работоспособность приложения после изменения.
2. Корректность админ-панели.
3. Отсутствие JavaScript ошибок в шаблонах.
4. Сохранение данных в `database.db`.

### Стиль вайб кодинга

- код должен быть `clean`;
- логика должна оставаться очевидной;
- не усложняйте там, где можно сделать проще;
- поддерживайте единый код-стиль и читаемость.

### Как работать с багами

1. Воспроизведите баг локально.
2. Найдите место в коде (`routers/`, `templates/`, `models/`).
3. Исправьте и проверьте.
4. Обновите документацию, если баг был в описании или поведении.

## Дополнительные советы

- `config.py` — основное место для глобальных настроек.
- `start.js` — служит для запуска приложения в среде с Node и автоматической установкой зависимостей.
- `backups/` — не храните здесь невалидные файлы, только рабочие копии.
- `exports/` — место для Excel-отчетов.

```bash
npm run dev
```
